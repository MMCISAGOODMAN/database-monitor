从 0 搭一套能投屏的数据库监控
database-monitor 2.1 实战手册

Docker 一键起 · 多库统一盯 · 告警能静默 · 操作可审计

别绕弯子。如果你同时管着 MySQL、PostgreSQL、Redis，甚至还有 Mongo，日常最大的成本不是「会不会 SQL」，而是切机器、切账号、切工具：状态散落在各处，告警来了才知道挂过，老板问健康度时还得临时拼表。

database-monitor 要解决的就是这件事：一套开源系统，把多库指标收到同一张可投屏大屏上，带告警、建议、对比和管理闭环。本文按「从 0 到能演示」写，夹一点设计取舍，方便你判断值不值得上、怎么配才像生产。

项目：github.com/MMCISAGOODMAN/database-monitor
版本：2.1.0（MIT）
栈：FastAPI + Vue3 + InfluxDB + Docker Compose
本机演示：http://localhost:8088 · admin / admin123

一、先想清楚：你到底要监控什么

监控系统最容易做成「数字博物馆」：KPI 很多，决策很少。上线前建议先划三条线：

1. 可用性：连得上吗？多久发现断连？

2. 容量与压力：连接比、QPS/OPS、内存/缓存命中是否逼近上限？

3. 质量：慢查询是否在涨？复制延迟是否失控？

database-monitor 的采集层按库类型拆 collector（MySQL / PG / Redis / Mongo），写入 InfluxDB 做时序，配置与告警落在 PostgreSQL。大屏走 HTTP + WebSocket：你看到的「实时」，本质上是短周期推送 + 本地缓存，不是魔法。

2.1 的一个关键修正：QPS、慢查询等用「计数器差分速率」，避免把 MySQL Questions 这种累计值直接当瞬时吞吐——后者会让告警阈值毫无意义。

二、从 0 启动：三分钟有界面

git clone https://github.com/MMCISAGOODMAN/database-monitor.git
cd database-monitor
docker compose up -d
# 打开 http://localhost:8088

默认账号 admin / admin123。登录页在 2.1 起默认是灰白高级感浅色，可一键切炭灰深色——投屏会议室用浅色更耐看，机房夜班用深色更护眼。

三、把「演示环境」配成「像生产」

只挂一个健康实例，大屏永远「岁月静好」，学不到排障。建议刻意配出三类状态：

正常：Compose 内 PostgreSQL、Redis（可同机不同 DB 索引做对比）

认证失败：宿主机 MySQL 故意错误密码 → 连接失败告警

网络不可达：Mongo / 假生产域名 → offline + 采集日志可追

再用分组切开：生产 / 预发 / 缓存层 / 文档库。分组不是装饰，它是大屏筛选和责任边界的入口。

实例级采集间隔（2.1）：核心库 10～15s，边缘库 60～120s。全局 tick 变短、实例各自节流——贵的库勤采，吵的库少采，这才是运维思维，而不是「所有指标 5 秒一轮」。

四、大屏怎么读：从 KPI 读到决策

打开大屏，先看五个 KPI：监控总数与异常、平均 QPS、总连接、今日告警、健康度。健康度被拖低时，优先看右侧告警流——多数时候是「某实例连不上」，而不是 CPU 真到了 99%。

左侧实例列表用状态筛选：正常 / 告警 / 故障。中间趋势图绑当前选中实例；底部热力图看相对负载，告警柱状图看近 7 日是否「今天特别吵」。读大屏的顺序建议固定成：异常数 → 告警内容 → 点进实例 → 建议/慢查询。

五、详情页：按库类型「看不同的数」

同一套「QPS / 连接 / CPU」卡片套所有库，是偷懒。2.x 起详情页会按 db_type 换卡片：MySQL 强调 Buffer 命中与慢查询速率；Redis 看命中率与内存；PG 看缓存命中与死锁。

「智能优化建议」输出的是结构化条目（等级、指标、阈值、动作），不是三句鸡汤。健康时诚实显示「暂无建议」；压力上来才给可执行项。告警根因也复用同一套顾问，避免大屏一套话、通知另一套话。

六、告警：规则、静默、渠道，三位一体

内置规则覆盖 CPU 代理负载、连接比、慢查询速率、缓存命中、内存等。自定义规则建议按环境拆：生产连接比更严、容量观察用 info 级，避免所有阈值都写成 critical。

静默（2.1）是给变更窗口用的：主从维护时把「主从延迟」静默 1～2 小时，到期自动恢复。静默期内不落新告警、不发通知，否则你的群会被变更本身刷爆。

通知渠道接企业微信 / 钉钉 / 飞书 Webhook 或邮件。可以留一个「飞书关闭、企微开启」的组合，演示灰度推送。记得：渠道配了不等于会响——规则要启用、且不在静默期。

七、对比与审计：从「看着」到「管得住」

勾选 2～3 个实例点「对比选中」，并排看 QPS、连接、CPU、命中率。典型用法：同机 Redis 不同 DB、或生产/预发同构库——一眼看出谁在吃资源。

八、几个容易踩的深坑

1. 假 QPS：累计计数当速率 → 阈值失真。2.x 已差分，升级后记得重评阈值。

2. max_connections：用 Max_used 当上限会让连接比算错；应读配置上限。

3. 删不掉实例：有告警外键时会失败；现在删除会先清关联。

4. 全库同一采集频率：核心库被拖慢、边缘库白采。用实例间隔拆开。

5. 变更不静默：维护窗口 = 告警风暴。静默是功能，不是偷懒。

写在最后

从 0 到能投屏，路径其实很短：Compose 拉起 → 配齐正常/故障实例 → 分组与间隔 → 规则与静默 → 渠道与审计。深度不在界面炫不炫，而在你是否用同一套系统把「看见、判断、通知、留痕」串起来。
